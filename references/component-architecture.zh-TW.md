# 元件架構

[English](component-architecture.md) · 繁體中文

當你要把線框或視覺模式轉成可重用的設計與實作系統時，使用本參考文件。

## 目標

頁面應由少量、責任清楚且一致的模式與元件組合而成。目標不是最大化抽象，而是建立可控重用。

## 輸入

改動元件架構前，檢視既有元件清單、設計 token、重複頁面模式、命名慣例、響應式和可及性行為、變體與狀態、重複樣式及一次性頁面實作。

## 重用決策順序

依序評估：重用 → 擴充 → 變體 → 組合 → 新建。

- **重用**：既有元件責任與內容模型已符合時，直接使用。
- **擴充**：新增能力屬於相同責任，且不會造成不穩定 API 時，擴充既有元件。
- **變體**：結構與責任相同，但呈現或密度有可預測差異時，新增有限的 variant。
- **組合**：需求是多個小型 primitive 的組合，而不是新的 primitive 時，組合使用。
- **新建**：現有元件無法清楚表達該模式時才新增。

## 偵測元件膨脹

警訊包括：名稱只差頁面脈絡、標記幾乎相同、以複製檔案表示變體、樣式只差少數數值、用商業名詞取代 UI 責任，或頁面元件洩漏到全域元件庫。

例如 FeatureCard、ProductFeatureCard、FeatureInfoCard、HomepageFeatureCard、EnterpriseFeatureCard，通常表示缺少 variant 或元件邊界不清。

## 責任原則

可重用元件應負責一項清楚的 UI 工作，例如 FeatureCard、PricingTable、TestimonialQuote 或 SectionHeader。

若元件名稱描述整個頁面流程，通常代表責任過多。也不要過度一般化；具有太多無關模式的元件可能暗藏頁面建構器。

## 元件契約

使用 templates/component-contract.zh-TW.md，定義用途、內容模型、變體、狀態、響應式行為、互動、可及性與組合規則。

## Token 邊界

重複視覺值原則上應先由 token 管理，不要直接在頁面覆寫。修正順序為：token → 元件 → 模式 → 頁面 → 一次性覆寫。若多個頁面都出現相同問題，不要逐頁修補。

## 頁面對照

實作前，把每個區塊對應到模式、元件與動作：

| 區塊 | 模式 | 元件 | 動作 |
|---|---|---|---|
| Hero | 產品主視覺 | Hero | 重用 |
| Benefits | 功能網格 | FeatureCard | 重用 |
| Metrics | 指標列 | MetricBand | 擴充 |
| Comparison | 比較表 | — | 新建 |

## 響應式行為

可行時在元件契約中定義響應式規則。手機版不是把桌面版壓成單欄；應檢查資訊優先順序、堆疊、換行、內容順序、互動、觸控範圍、溢位、圖片裁切與表格行為。

## 可及性

只有保留可及性行為時，重用才有價值。契約應依適用情況定義語意、可及名稱、鍵盤支援、焦點行為、錯誤/空/載入狀態、對比與減少動態效果。

## 變更治理

新增頁面需求時：先檢查既有模式，再對照線框、說明每項新建元件、先建立缺少的共用 primitive、組合頁面，最後再次檢查重複。

## 驗收 gate

確認重複模式使用共用元件、元件責任容易理解、variant 範圍受控、近似元件已整併、重複視覺決策由 token 管理、響應式行為有定義、可及性行為保留，且頁面覆寫屬於例外。

## 最低交付內容

元件清單、重複問題、元件對照、新建或擴充的元件契約、token 變更、遷移影響與驗收結果。
